# 01_项目说明书

> 项目名称：RE:FUDAN（复见）  
> 小组名称：复见组  
> 材料类型：Agent 训练营中期材料

## 1. 项目目标

### 1.1 要解决的问题

复旦校园内存在大量“经验供给丰富，但连接成本很高”的咨询场景，例如保研、夏令营、科研、实习、转轨、申请等。当前常见问题包括：

- 学弟学妹不知道“应该先问谁”
- 学长学姐要重复回答大量相似问题
- 传统社交方式往往先加好友，再判断是否匹配，冷启动摩擦很高
- 经验传递缺乏结构化、可追踪、可分阶段推进的机制

### 1.2 我们的方案

RE:FUDAN 希望把“找人问经验”改造为“先由 Agent 完成一轮高质量预沟通，再决定是否进入真人接力”的流程。

当前工作版的主链路是：

1. 学弟先构建自己的 Agent 档案
2. 系统基于档案与问题方向推荐更合适的学长
3. 在需求匹配页发出第一句问题后，学弟 Agent 与学长 Agent 自动完成数轮 A2A 预沟通
4. 系统生成总结、结论和回流评分
5. 学长侧在接力收件台决定是否 handoff
6. 若通过，则进入 P4 连接简报，推动真人连接

### 1.3 一句话概括

让经验先抵达，答案再相见。

## 2. 当前 Demo 功能

### 2.1 学弟侧能力

- 注册 / 登录
- 在 Agent 工作台中构建个人 Agent 档案
- 通过简历文本或社媒账号触发画像抽取与分析
- 在 `/me/junior` 选择当前问题方向
- 获取围绕该方向重排后的学长推荐
- 在推荐卡片内直接输入第一句问题并启动 A2A 自动多轮预沟通
- 查看自动生成的结论、摘要、覆盖槽位和回流评分
- 进入 P3 会话中心查看完整轨迹并继续手动追问

### 2.2 学长侧能力

- 注册 / 登录
- 维护个人 Agent 档案
- 在 `/me/senior` 查看接力收件台
- 查看进入 handoff 视野的会话摘要和评估结果
- 进入 P3 会话中心查看完整 A2A 轨迹
- 决定 `approved / rejected`
- 进入 P4 连接简报页，标记“准备完成 / 连接完成”

### 2.3 系统侧能力

- 推荐结果缓存与回流更新
- A2A turn / trace / assessment 持久化
- autoplay 状态管理
- handoff / referral 状态管理
- 画像构建结果写回用户档案

## 3. 系统设计

### 3.1 总体结构

当前系统由三层组成：

1. 前端与业务 API 层
2. 状态存储与会话层
3. 外部能力层

#### A. 前端与业务 API 层

位置：

- `apps/site/src/app`

承担：

- 页面渲染
- 登录注册
- 推荐与搜索
- A2A 会话创建、推进、查看
- handoff / referral 操作
- 画像流水线触发

#### B. 状态存储与会话层

位置：

- `apps/site/src/lib/redis.ts`
- `apps/site/src/lib/users-redis.ts`
- `apps/site/src/lib/chat-redis.ts`

承担：

- 用户信息存储
- 登录 session 管理
- 学长 / 学弟索引
- 推荐缓存
- A2A session metadata
- turn / trace / assessment / handoff / referral 记录

当前使用：

- Upstash Redis（REST 模式）

#### C. 外部能力层

包括两部分：

1. DeepSeek API
2. Python 画像流水线

DeepSeek 用于：

- 学长 Agent 回复生成
- 自动多轮 A2A 中的 senior-side 回复

Python 流水线用于：

- GitHub / 小红书 / 知乎 / LinkedIn 资料采集
- 画像分析与综合
- 生成结构化 Agent 档案

### 3.3 A2A 自动多轮设计

这部分是当前版本最核心的更新。

#### 主触发点

主触发点已前移到 `/me/junior` 的需求匹配页。

用户在推荐卡片中写下第一句问题后：

1. 创建带 `autoplay: true` 的 session
2. 完成首轮回复
3. 前端循环调用 autoplay API，逐轮推进
4. P3 保留完整轨迹，需求匹配页展示总结和结论

#### 5 个信息槽

当前动态骨架围绕以下 5 个槽位推进：

- 入营 / 整体难度
- 真题 / 问题类型
- 导师或沟通风格
- 信任升级后才适合透露的信息
- GPA / 硬门槛

#### 停止条件

系统不会写死 5 到 7 轮台词，而是：

- 默认总轮数上限为 `7`
- 当关键槽位覆盖足够，且结论置信度达到阈值时提前停止
- 若模型调用失败，则保留已生成内容并降级结束

#### 输出结果

自动多轮完成后，系统会生成：

- `summary`
- `verdict`
- `adjustedScore`
- `insights[]`
- `coveredSlots[]`

这些结果会回流到推荐页对应学长卡片。

### 3.4 P3 与 P4 的角色拆分

当前项目把 P3 和 P4 明确拆开：

- P3 负责完整 A2A 轨迹、assessment、trace、人工继续追问
- P4 负责 handoff 后的连接简报、状态推进与真人接力

这种设计可以让“Agent 预沟通”和“真人连接”边界更清晰。

## 4. 当前完成情况

### 4.1 已完成内容

截至当前版本，已经完成：

- 登录 / 注册 / 角色身份体系
- 基于 Upstash Redis 的服务端 session
- demo 学长 seed 脚本
- Agent 工作台
- 学弟需求匹配页与推荐页
- 学长接力收件台
- P3 A2A 会话中心
- P4 连接简报页
- A2A turn / trace / assessment 持久化
- autoplay 编排与逐轮推进 API
- assessment 回流到推荐结果
- Python 画像流水线接入
- DeepSeek 对话生成接入
- 旧 `agent-workbench` 入口兼容 autoplay

### 4.2 当前可演示链路

目前可以稳定演示的完整链路是：

1. 注册学弟账号
2. 构建 Agent 档案
3. 进入需求匹配页
4. 选择问题方向并输入第一句问题
5. 触发 A2A 自动多轮对话
6. 查看自动总结、结论与回流评分
7. 进入 P3 查看完整轨迹
8. 切换到学长账号查看接力收件台
9. 决定 handoff
10. 若通过则进入 P4 连接简报

### 4.3 当前限制

- 当前自动多轮更接近“编排式双 Agent”，还不是完全自由博弈的双智能体
- `coveredSlots` 目前表示“该类问题已被追问/覆盖”，不完全等于“高质量确认完毕”
- DeepSeek 不可用时会自动降级为 fallback reply，流程尽量不断，但质量会下降
- Python 画像流水线仍依赖本地环境，部署复杂度较高

## 5. 运行效果与亮点

### 5.1 当前版本亮点

- 需求匹配页可以直接发起 A2A，不再强依赖跳转到单独创建页
- 自动多轮对话后能生成结构化 summary / verdict / score
- 推荐与会话中心实现了“回流联动”
- P3 与 P4 边界清晰
- 旧入口也已接入自动多轮链路，演示路径更稳

### 5.2 评审可重点关注的部分

- `/me/junior` 中“首句问题驱动 A2A 自动多轮”
- P3 会话中心中的自动轨迹与 assessment
- 学长侧的 handoff 决策与 P4 接力
- Redis + DeepSeek + Python 流水线共同支撑的真实系统感
